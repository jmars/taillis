## 6. Numeric check — the part that rules out a silently wrong artifact

Method. The fp8 decode is an **independent bit-level E4M3 "FN" lookup table** (sign 1 / exp 4
bias 7 / mantissa 3, no infinities, only `exp=15,mant=7` is NaN, max 448), **not** torch's cast.
The table was validated against `torch.float8_e4m3fn` on all 256 codes: **IDENTICAL**. The scale is
applied as `(decode(w).float32 * scale.float32)`, exactly as `conversion/base.py dequant_simple`
does with `weight_block_size = null` (per-tensor and per-expert scales, dims aligned by appending
singleton axes), and compared elementwise against the F16 GGUF after the same
`astype(np.float16)` the writer performs.

**Negative control (the asymmetry, required).** Every comparison is run twice — with the scale and
without it. With the scale the equality must be total; without it the comparison must **fail**,
otherwise the check could not detect the failure it exists for. The scale values are 1.5e-4 …
3.6e-3 and no scale tensor is all-ones (`logs/t12-scale-sanity.log`), so "with scale" and
"without scale" are materially different.

**(a) Narrow check — one tensor per fp8 layout kind and per non-fp8 kind** (`logs/t12-numeric-check.log`, exit 0)

| `self_attn.o_proj.weight` (layer 17) | 1.1673e-3 scalar | 16,777,216 | **all exactly equal** | 1240 equal (max\|Δ\| 447.5) |

**(c) Scale sanity, all layers** (`logs/t12-scale-sanity.log`): all **360** `_scale_inv` tensors

## 9. Measured correction to the "E4M3 → F16 is lossless" claim

The plan states E4M3 → F16 is *exact*, so the conversion is lossless. Measured, it is exact in the
fp8→f32 step (every E4M3 code × scale is a correctly-rounded f32 product) but the f32→f16 **store
rounds**:

| tensor | elements | exactly representable in F16 | max absolute rounding | max relative, F16 normal range | max relative, subnormal range |
|---|---|---|---|---|---|
| L0 `self_attn.q_a_proj` | 4,194,304 | 99.796% | 2.98e-8 | 0 (evaluated 0) | 3.70e-2 |
| L0 `experts.gate_up_proj` exp 0 | 16,777,216 | 99.817% | 2.98e-8 | 0 | 1.03e-2 |
| L0 `experts.down_proj` exp 0 (scale 2.05e-4) | 8,388,608 | **68.627%** | 3.05e-5 | 4.23e-4 | 4.19e-2 |
| L0 `shared_experts.down_proj` (first 2048 elements) | 2,048 | 99.951% | 2.98e-8 | 0 | 1.57e-3 |

So: 0.2–31% of elements are rounded, at ≤ f16's half-ulp (4.88e-4 relative; measured max in the
normal range 4.23e-4 — the worst case is the tensor with the smallest scale, whose values need the
most mantissa bits for their exponent). Values that fall below f16's smallest normal (6.1e-5;
~0.4% of elements) are stored as f16 subnormals with coarser relative error (up to 4.2e-2) but a
bounded absolute error — measured max absolute rounding over these tensors: **3.05e-5**, one f16
subnormal step. The artifact is therefore faithful to the source's fp8 codes *and* scales, and is
F16-rounded rather than bit-lossless against the mathematical dequantized weights (which is what
`--outtype f16` asks for).

* **No content hash** of the 238 GB artifact was recorded (a `sha256sum` costs ~15 min of I/O on a

* The verification scripts (E4M3 table, layout oracle, accounting, narrow check, sweep, scale
